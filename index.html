Pick a model and a GPU setup. The platform schedules the job onto real GPUs, serves the model, load-tests it with realistic traffic and reports what the customer will actually experience.

  • Latency: time to first token (TTFT), time per output token (TPOT), inter-token latency (ITL), end-to-end latency — median, P95, P99
  • Throughput: requests/s, output and total tokens/s
  • Hardware: per-GPU utilisation and memory, sampled live through NVML

Results export as Excel and a customer-ready PDF, and can be shared over Slack.

Internal tool · code is proprietary

Distributed system

Router, GPU workers & scheduler

A FastAPI router with MongoDB and JWT/MFA auth, and one GPU worker node per GPU type. Jobs enter a global queue; a multi-GPU scheduler reserves the GPUs each job needs, with a guard against double scheduling. A background reconciler syncs results exactly once, prevents duplicate notifications and times out stuck jobs.

Engine abstraction

vLLM and SGLang, one interface

Both engines run from their official Docker images, pinned to the assigned GPUs. Each engine only answers how to launch, connect, benchmark and stop — so adding a new engine is one class, and every engine reports the same metrics.

Prevent failures

Memory-fit estimator

Before a run starts, it predicts whether the model fits in GPU memory: exact weight size from Hugging Face safetensors metadata, KV cache from the attention config (including DeepSeek-style MLA and Mamba / Gated-DeltaNet hybrids) and runtime overhead, against usable VRAM. If it won't fit, the Run button is disabled — no GPU time wasted on an out-of-memory crash.

Decision support

GPU sizing recommender

Runs the fit estimator over every GPU type and count, and recommends the fewest GPUs, then the smallest GPU that's enough. Shows a compatibility matrix across 1, 2, 4 and 8 GPUs with estimated monthly cost, and applies a recommendation to the benchmark form in one click.

Own initiative

Deterministic error analyzer

Most failed runs became tickets to the ML team, even when the fix was a config change. I built a 33-rule classifier that splits failures into user-fixable — naming the exact field and often the exact value to change — and escalate. No LLM by design: the same error must always get the same answer. Unknown errors are normalised into signatures so the team knows which rule to write next.

Reliability & UX

Making it production-grade

Waits for GPU memory to actually free before reusing a GPU, falls back to a free port on collisions, and supports clean stop. Added run-time ETA learned from past runs, "already benchmarked?" search over similar historical runs, side-by-side comparison of runs, and Slack result sharing.

What can you actually forecast about NIFTY from its own price history? Direction failed every honest test. The range — how far it will move — is predictable, because volatility clusters.

COMBO blends EWMA, India VIX and long-run volatility in log-variance space, fitted by maximum likelihood, with filtered historical simulation to keep real fat tails. Its 1-day forecasts beat RiskMetrics, GARCH(1,1), historical volatility and raw VIX on CRPS, QLIKE and interval score, and it was the only model to pass the Kupiec and Christoffersen VaR tests at both 95% and 99%.

Every direction idea — Markov chains on 5-minute candles, a volatility-breakout strategy, a support/resistance + ADX strategy — failed to beat random entries, and is reported as such. No look-ahead, yearly refits, non-overlapping samples, |t| ≥ 2 required.

An end-to-end fine-tuning pipeline: ~31K curated and de-duplicated code samples → rank-16 LoRA on a 4-bit NF4 base → merge → GGUF export → OpenAI-compatible FastAPI server and Streamlit UI.

The hard part was after training: merging a 54 GB model on CPU, stripping 439 unused vision tensors, and a GGUF tokenizer bug that silently deleted variable names from generated code. The 3060 can't hold 16 GB, so 25 of 62 layers run on the GPU and the rest on CPU.

MBPP stays in line with the base model, so the fine-tune changed style and structure without losing capability. HumanEval is being re-measured on a corrected harness against the base model.
